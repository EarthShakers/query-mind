# spark game 代码生成“卡住 / 不流式”问题复盘

## 背景

在 `spark game` 的早期实现里，用户输入需求后，CLI 通常会先快速看到一段「构建计划」，但一进入真正写代码阶段，体验会明显变差：

- 终端看起来像卡住
- 左侧编辑器要么长时间没有代码，要么一下子跳出整份文件
- 右侧预览通常要等全部完成后才会刷新
- 用户很难判断当前到底是“模型还在思考”、还是“已经开始写代码”、还是“请求已经卡死”

这个问题在复杂游戏生成时尤其明显，例如：

- 多文件游戏
- 单文件超长 `index.html`
- 先 `read_file` 再修改现有游戏
- 包含参数面板、关卡系统、粒子特效等复杂需求

## 最初现象

典型表现如下：

1. 构建计划能快速流式输出
2. 之后长时间只看到“思考中...”或一条很短的进度说明
3. 真正的代码内容几乎不可见
4. 最后直接出现：
   - 某个文件被写入完成
   - 或请求超时
   - 或连接中断

对用户来说，体感就是：

- “计划是流式的，为什么写代码不是？”
- “到底有没有开始生成代码？”
- “为什么左侧看不到实时过程？”

## 第一层根因：文本流和 Tool Call 流不是一回事

问题的核心不在 `readline`，也不在终端刷新本身，而在协议层。

### 计划为什么很流畅

构建计划走的是普通文本流：

- 模型逐 token 输出文本
- `streamText` 把文本片段不断下发
- CLI 直接把文本打印到终端

这条链路天然适合“流式可见”。

### 写代码为什么不流畅

早期方案里，写代码走的是 `tool_call -> write_file(path, content)`：

- 模型不是把代码作为普通文本输出
- 而是把完整代码塞进工具参数 `content`
- 这部分内容在 SDK / 模型服务侧通常会被组织成更大的 JSON 片段
- 所以即使底层也是流，也往往是“大块吐出”，不是普通文本那种平滑 token 流

结果就是：

- 用户能看到计划
- 但真正代码阶段像突然没动静
- 直到某个文件整块完成才看见结果

## 第二层根因：复杂游戏单文件过大

另一个放大问题的因素是：

- 复杂游戏如果全塞进一个超长 `index.html`
- 单次 `write_file(content)` 会非常大
- 上游模型生成耗时更长
- 下游 JSON 参数流也更粗

这会让“写代码阶段像卡住”的感觉更严重。

## 第三层根因：预览层对多文件游戏不友好

后续在支持“每个游戏一个 slug 目录”时，又暴露出一个多文件预览问题：

- 右侧 iframe 最初使用的是 `/index.html?game=<slug>`
- 这样入口 HTML 虽然能按 slug 打开
- 但 HTML 内部的相对资源请求，比如 `game/style.css`
- 实际会发成 `/game/style.css`
- 请求里没有携带 `game=<slug>`
- 服务端就可能回到默认目录查找

这会导致：

- 单文件游戏正常
- 多文件游戏样式 / 脚本失效
- 用户误以为“HTML 被改坏了”

本质上其实是资源路径命名空间丢了。

## 一路尝试过的方案

在最终定型前，做过几轮中间方案。

### 1. 继续沿用 `write_file`，只增强阶段提示

做过这些改动：

- 增加更明确的 spinner 文案
- 工具执行后打印阶段日志
- 在 `read_file` 后补一句“正在继续修改...”
- 把超时和中断错误翻译成用户可理解的提示

这些优化有帮助，但没有触及最核心的问题：

- 代码仍然躲在 `tool_call` 的 JSON 参数里
- 所以“流式看代码”这件事本质上还是不顺

### 2. 从 `tool_call` 参数里提取草稿，推给左侧编辑器

这是中间阶段比较重要的一步：

- 在 CLI 里解析 `tool_call_delta`
- 从 `write_file.content` 的部分 JSON 字符串里尽量恢复代码草稿
- 把草稿推送到 `/spark` 左侧
- 右侧仍然只在真实写入完成后刷新

这样做解决了两个问题：

- 左侧终于能看到“代码长出来”
- 右侧不会因为半截 HTML/JS 频繁报错

但它仍有局限：

- 草稿来源还是工具参数流
- 粒度仍受 JSON 分块影响
- 视觉上还是不如普通文本流丝滑

### 3. 把复杂游戏默认改成多文件

后续又调整了 prompt：

- 简单游戏才单文件
- 复杂游戏默认拆成多文件
- 优先 `index.html + game.js + style.css`

这能减少单次输出体积，但仍然没有完全解决“代码阶段不够流式”的本质问题。

## 最终方案：改协议，不再用 `write_file` 输出代码

真正解决问题的关键，是把“写代码”从工具调用协议里拿出来。

### 最终协议

服务端仍然保留 `read_file` 用于读取现有代码，但写文件不再通过工具调用，而是要求模型直接输出普通文本：

````md
FILE: index.html
```html
...完整文件内容...
```

FILE: game/game.js
```js
...完整文件内容...
```
````

也就是：

- `FILE: 相对路径`
- 紧接一个 Markdown 代码块
- 代码块结束后再进入下一个文件

### 这样做为什么有效

因为这时代码重新回到了“普通文本流”里：

- 模型生成代码时，和输出构建计划走的是同一类文本流
- CLI 只需要边收文本边解析 `FILE:` 和代码块
- 左侧草稿可以实时增长
- 文件闭合时再原子写盘

这相比 `tool_call(write_file)` 有几个明显优势：

1. 代码阶段终于能像普通文本一样流式可见
2. CLI 不再依赖从 JSON 参数里“猜”代码草稿
3. 文件级边界更清晰，适合多文件游戏
4. 右侧仍然可以保持“只在完整写盘后刷新”的稳定体验

## 当前实现细节

### 服务端：只保留 `read_file`

文件：

- `src/app/api/game/route.ts`

当前游戏 API：

- 保留 `read_file`
- 移除 `write_file`
- 模型通过普通文本流输出 `FILE:` + code fence

### Prompt：强制使用文件输出协议

文件：

- `src/lib/game/prompts.ts`

关键规则：

- 先输出构建计划
- 不要通过 `write_file` 输出代码
- 对复杂游戏默认使用多文件
- 每个文件必须按 `FILE:` + 代码块格式输出

### CLI：流式解析文件块

文件：

- `cli/src/chat.ts`

CLI 现在会：

1. 持续接收普通文本流
2. 识别 `FILE: path`
3. 进入对应代码块
4. 把代码块内容当作“生成中的草稿”实时推给左侧编辑器
5. 代码块闭合时，把完整文件写到磁盘
6. 写入后刷新右侧预览

### 预览：多游戏、多文件都按 slug 命名空间加载

文件：

- `cli/src/preview.ts`

预览侧做了几件关键事：

1. 每个游戏使用独立 slug 目录
   - `games/<slug>/index.html`

2. `/spark` 支持切换不同游戏目录

3. 右侧 iframe 使用命名空间路径
   - `/__spark/game/<slug>/index.html`

这样 HTML 里的相对资源：

- `game/style.css`
- `game/game.js`

也会自然落到：

- `/__spark/game/<slug>/game/style.css`
- `/__spark/game/<slug>/game/game.js`

从而解决多文件游戏资源加载错误的问题。

## 目录组织上的配套调整

为了解决多个游戏混在 `games/default` 的问题，当前约定变成：

- 每个游戏一个 slug 目录
- 每个游戏目录都有自己的 `index.html`
- 复杂游戏可以在该目录下再放 `game/`、`assets/` 等子目录

例如：

```text
games/
  flappy-bird/
    index.html
  memory-card/
    index.html
    game/
      style.css
      cards.js
      game.js
  tank-battle/
    index.html
```

这样 `/spark` 顶部就能直接切换不同游戏。

## CLI 交互上的配套调整

为了减少使用成本，还补了两层交互优化：

### 1. `spark game` 支持直接传 slug

例如：

```bash
spark game memory-card
```

等价于：

```bash
spark game -g memory-card
```

### 2. 不传参数时自动列出已有游戏

也就是：

```bash
spark game
```

会列出现有 `games/` 目录，让用户选择，而不是默认所有东西都写进 `default`。

### 3. `spark --help` 增强

在：

- `spark --help`
- `spark game --help`
- `spark preview --help`

里增加了实际可复制的命令示例。

## 现在解决了哪些问题

到目前为止，已经解决的问题包括：

1. 代码生成阶段不再完全“黑盒卡住”
2. 左侧编辑器能在生成过程中看到代码草稿
3. 文件写入完成后会明确提示完成
4. 复杂游戏默认更适合使用多文件
5. 每个游戏都有独立 slug 目录
6. `/spark` 可以切换不同游戏
7. 多文件游戏的相对资源能按 slug 正确加载

## 仍然存在的边界

虽然体验已经比最初好很多，但仍有一些现实边界：

### 1. 代码阶段不一定像字符级打字机那样丝滑

原因是：

- 即使代码已经走普通文本流
- 上游模型/SDK 有时仍会按块吐出内容
- 所以体验会明显好于 `tool_call` 方案，但未必永远达到“一个字符一个字符”那种视觉效果

### 2. 当前仍然是“整文件输出”，不是 Diff 模式

也就是说：

- 修改已有游戏时，通常是读取现有文件后输出完整新文件
- 不是精确到几行的 patch

这是当前方案为了稳定性做的取舍。

## 后续可继续优化的方向

### 1. 真正的 Diff / Search & Replace 模式

例如：

- `search_block` / `replace_block`
- `rewrite_lines(start, end, content)`

优点：

- 输出更短
- 修改更快
- 复杂项目更稳

但实现复杂度会高很多，需要额外处理：

- 唯一匹配
- 失败回滚
- 多处重复块

### 2. 终端“打字机平滑化”

即使上游一坨坨来，也可以在 CLI 里做队列缓冲：

- 下游固定速度显示
- 让用户感觉更像持续生成

这属于体验层优化，不改变协议本身。

### 3. 左侧编辑器高亮新增区域

当前左侧已经能看草稿，后面还可以继续做：

- 自动滚到新增位置
- 高亮最近新增片段
- 显示当前正在生成哪个文件

### 4. 游戏修改模式专门优化

当前生成新游戏和修改旧游戏共用一套主流程。未来可以进一步拆分：

- 新建游戏：偏多文件 scaffold
- 修改游戏：偏最小必要改动

## 结论

这次问题的真正根因，不是终端刷新，不是 `readline.pause()`，也不是单纯“模型慢”，而是：

- 构建计划走的是普通文本流
- 代码写入走的是 `tool_call(write_file)` 参数流

两者天然不是同一类体验。

最终有效的解决方式是：

1. 保留 `read_file`
2. 移除 `write_file` 作为代码输出协议
3. 改为 `FILE: path + Markdown code fence`
4. CLI 实时解析并推送草稿
5. 文件闭合时再原子写盘
6. 预览按 slug 命名空间加载多文件资源

这套方案把“看起来卡住”的问题，从协议层真正解决掉了，而不是只在 UI 上打补丁。
